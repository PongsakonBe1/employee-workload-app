# ตาราง UAT สิทธิ์/การเพิ่มพร้อมกันบน staging

สถานะล่าสุด: ผู้ใช้อนุมัติชุด QA แล้ว และทดสอบ concurrent writes ผ่าน Google ของบัญชีผู้ทดสอบเดิมใน Edge สองแท็บสำเร็จ 3 กรณี เพิ่มจริง 4 ตาราง / 4 receipts / revision 5 → 9 เหลือ PDF negative batch ที่ยังเลือกไฟล์ไม่ได้เพราะ extension file-URL permission ดู [ผล cloud](cloud-uat-results.md) ไม่มีการสร้างบัญชี เปลี่ยนสิทธิ์ หรือ deploy

## เงื่อนไขก่อนเริ่ม

- เป้าหมายเฉพาะ `labboy-workload-app-staging` และหน้า `/dev/calendar-staging-write`
- ยืนยันว่าผู้ทดสอบมี Google sign-in ของแต่ละบทบาทและ profile/capability ที่ผู้ดูแลกำหนดแล้ว ไม่ส่ง credentials ให้ agent
- หากมีเฉพาะ Admin เดิม จะตรวจได้เฉพาะ Admin และ concurrency สอง session ของบัญชีเดียว; Staff/Superadmin บน cloud ต้องคงสถานะรอ ไม่อนุมานจาก Emulator
- ตกลงชุดรายการสังเคราะห์ที่ระบุ prefix `QA` และช่วงวัน/ห้อง/เวลาที่ตรวจแล้วว่าง ไม่ใช้ตารางจริงเป็นตัวทดสอบ ไม่แก้วันของข้อมูลนำเข้าเพื่อหลบ conflict
- การเพิ่มชุด QA, การเปิด capability ให้บัญชีใหม่ หรือการเก็บกวาดรายการ QA บน cloud ต้องมีขอบเขตที่อนุมัติชัดเจนก่อนลงมือ ไม่เปิด Auth provider เพิ่มหรือเปลี่ยนบทบาทบัญชีเดิมโดยอัตโนมัติ

## Role matrix

| บัญชี | การตรวจ | ผลที่คาด | สถานะ |
|---|---|---|---|
| ไม่เข้าสู่ระบบ | อ่านและปุ่มนำเข้า | ไม่อ่านข้อมูล / ปุ่มปิด | ผ่าน: SDK ปฏิเสธ 4 QA references; ปุ่มปิดก่อน login |
| Staff active | อ่าน, เพิ่ม/นำเข้า | อ่านได้ / เพิ่มไม่ได้ | รอบัญชี |
| Admin active + capability | เพิ่มรายการสังเคราะห์ | เพิ่มได้และโหลดกลับถูกต้อง | UAT เพิ่ม/นำเข้าเดิมผ่าน; รอชุด matrix |
| Superadmin active + capability | เพิ่มรายการสังเคราะห์ | เพิ่มได้ | รอบัญชี |
| Admin/Superadmin ไม่มี capability | ทดลองเพิ่ม | ปฏิเสธ | รอบัญชีที่กำหนดไว้ ไม่ downgrade บัญชีจริง |
| Pending/inactive | อ่านและเพิ่ม | ปฏิเสธ | รอบัญชี |

การทดสอบผ่าน UI ยืนยันเฉพาะพฤติกรรม UI และผลที่ผู้ใช้เห็น การพิสูจน์ rules ด้วยคำขอ SDK โดยตรงต้องใช้ SDK ที่ sign-in ตามปกติภายใต้บัญชีนั้น ไม่คัดลอก token ออกจาก browser หรืออ้างผล privileged admin request

## Concurrency matrix

| กรณี | ชุดทดสอบที่ต้องเตรียม | ผลที่คาด |
|---|---|---|
| ชนกัน | สองชุดชื่อ QA ต่างกัน แต่วัน/ห้องเดียวกันและเวลาซ้อน | เพิ่มได้หนึ่งชุด อีกชุดแจ้งชน ไม่มีรายการบางส่วน |
| ชุดเดียวกัน | ข้อมูล QA ตรงกันทุก field จากสอง session | สร้างเพียงหนึ่งชุด / อีก session ข้ามหรือแจ้งซ้ำ |
| ไม่ชนกัน | เวลาเดียวกันแต่คนละห้อง | เพิ่มได้ทั้งสองชุด |
| ชุดผสม | หนึ่งรายการว่าง + หนึ่งรายการที่ชนกับ QA ที่เพิ่มไว้ | ทั้งชุดไม่ถูกบันทึก |
| Reload/sign-in | โหลดใหม่ด้วยสิทธิ์เดิมหลังแต่ละกรณี | จำนวนรายการและรายละเอียดตรงกับผล commit |

ก่อนเริ่มจริงต้องเติมวัน เวลา ห้อง และชื่อ QA ให้ครบในรายการที่ผู้ใช้ตรวจได้ แล้วจึงอนุมัติรันบน cloud ไม่ถือว่าการเตรียมตารางนี้เป็นการอนุมัติให้เขียน cloud ทุกกรณีหรือ deploy production

## ชุดรายการที่เตรียมแล้ว

เป้าหมาย `labboy-workload-app-staging` ภาคเรียน `2/2569` ไม่ระบุผู้สอน ใช้บัญชีผู้ทดสอบเดิมที่ตรวจ writer capability แล้วในสอง session อิสระ การทำได้ด้วยบัญชีเดียวไม่ทดแทนการตรวจ Staff/Superadmin หลายบัญชีบน cloud

| กรณี | วัน/ห้อง/เวลา | ชื่อรายการ | คาดว่าเพิ่มจริง |
|---|---|---|---|
| ชนกัน | 19 เม.ย. 2570 ห้อง 401: A 10:00–11:00 / B 10:30–11:30 | `QA-CLOUD-OVERLAP-A` / `QA-CLOUD-OVERLAP-B` | 1 |
| ส่งซ้ำพร้อมกัน | 20 เม.ย. 2570 ห้อง 402 10:00–11:00 ข้อมูลตรงกันทั้งสอง session | `QA-CLOUD-IDENTICAL` | 1 |
| คนละห้อง | 21 เม.ย. 2570 ห้อง 401 และ 402 เวลา 10:00–11:00 | `QA-CLOUD-ROOM-401` / `QA-CLOUD-ROOM-402` | 2 |
| batch ต้องถูกปฏิเสธ | 19 เม.ย. ห้อง 401 10:00–11:30 + 22 เม.ย. ห้อง 402 14:00–15:00 | `QA-CLOUD-ATOMIC-COLLISION` / `QA-CLOUD-ATOMIC-GOOD` | 0 |

รายละเอียดเครื่องอ่านได้อยู่ใน `staging-fixtures.json` คาดว่าจะเพิ่มไม่เกิน **4 ตาราง / 4 receipts / revision เพิ่ม 4** หากผลตรงตามแผน ไม่แก้เอกสารที่ผู้ใช้เคยนำเข้า ตาราง QA ที่เพิ่มจริงจะคงอยู่จนตรวจผลและตกลงเก็บกวาดเฉพาะรายการเหล่านั้น

กรณี negative batch ใช้ `output/pdf/calendar-role-concurrency-qa/staging-atomic-qa.pdf` ในโหมด PDF import เลือกช่วงกลุ่ม ป.ตรี/อื่น ๆ **19–22 เม.ย. 2570** และภาคเรียน `2/2569` มี 2 rows ที่ parser ตรวจตรง manifest แล้ว ทั้งสองมีคาบเพียงครั้งเดียวในช่วงนี้ แม้ validTo ของรายการวันจันทร์เป็นวันพฤหัสบดีที่ 22 เม.ย. ต้องรันหลังกรณี overlap มีผู้ชนะก่อน จึงคาดว่าทั้ง batch จะถูกปฏิเสธ

`qaPreflight` อ่านแบบ field projection เฉพาะห้อง วัน และเวลาจาก 25 ตารางเรียน active และรอบสอบ 0 รายการในช่วงนี้ พบว่าง ณ เวลาที่ตรวจ ดู `cloud-preflight.json` ซึ่งผูก SHA-256 ของ manifest ไว้ ผลนี้ไม่ใช่การจองช่วงเวลาและไม่ใช่หลักฐาน rules เพราะใช้ CLI ที่มีสิทธิ์จัดการ ก่อน commit จริง writer ยังต้องตรวจข้อมูลล่าสุดตาม protocol

## การเข้าสู่ระบบที่ต้องดำเนินต่อ

เปิด writer staging ใน browser แยกแล้ว ก่อน Google login เห็นปุ่มเพิ่ม/นำเข้าปิดอยู่ แต่การเชื่อมต่อ Edge หลุดหลังเริ่ม Google flow จึงยังไม่ยืนยัน authenticated session และไม่เขียน cloud ขอให้ผู้ใช้เปิดการเชื่อมต่อ browser อีกครั้งและเข้าสู่ staging ตามปกติ ไม่มีการอ่านหรือคัดลอก token เพื่อข้ามขั้นนี้

ผู้ใช้อนุมัติชุดรายการข้างต้นแล้วเมื่อ 10 พฤศจิกายน 2569 โดยผูกกับ SHA-256 `43dfd0c8723f74dd84c549d9794b8504ed696d8c2b9f6dad6f6281ec8173191f` ของ manifest ไม่ต้องขออนุมัติชุดเดิมซ้ำ การตรวจซ้ำเวลา 16:35 น. (Asia/Bangkok) พบช่วง QA ว่าง writer enabled และ revision 5 แต่ Edge/Chrome ยังไม่ปรากฏใน browser inventory จึงยังไม่ส่งคำขอเขียนหรืออ้างว่าทดสอบ concurrency แล้ว

หลังเชื่อมต่อและเข้าสู่ระบบตามปกติได้ จึงเปิดสอง session ตรวจแบบฟอร์มและส่งพร้อมกัน เก็บหลักฐานผล UI/จำนวนรายการที่สร้าง/สถานะ reload โดยไม่อ้างว่าเห็นการ retry ภายใน SDK หากมีเพียงหลักฐานจาก UI และไม่ใช้ CLI ที่ bypass rules มาแทนผู้ทดสอบ

### ยืนยัน session A และ baseline แล้ว

ต่อมา Edge เชื่อมต่อได้จริง และหน้า `/dev/calendar-staging-write` ของ session A แสดงอ่านสำเร็จ 25 ตารางเรียน / 18 รอบสอบ พร้อมเปิดปุ่มเพิ่ม/นำเข้า จากนั้นเปิดแท็บ session B แยกและเริ่ม Google sign-in ตามปกติ แต่การเชื่อมต่อ Edge หลุดหลังเปิด Google จึงรอผู้ใช้เลือกบัญชีเดิมและเชื่อม Edge กลับมา ยังไม่กรอกหรือส่งรายการ QA ใด

เพิ่ม `qaAudit before|after` ในเครื่องมือตรวจ staging เพื่อคำนวณ document/receipt IDs จาก manifest ที่อนุมัติ แล้วใช้ read-only `batchGet` พร้อม field mask เฉพาะข้อมูล QA ไม่มี fields ชื่อผู้ใช้/UID/tokens ผล `cloud-storage-audit-before.json` ยืนยัน QA schedules 0, QA receipts 0 และ revision 5 ผ่าน 14 คำขออ่าน ต้องเก็บ baseline ใหม่ก่อนเริ่มจริงหากมีงานเขียนอื่นระหว่างรอ การตรวจแบบ privileged นี้ยืนยันเฉพาะสถานะที่จัดเก็บ ไม่ใช้แทนหลักฐานสิทธิ์หรือ concurrency ของ browser
